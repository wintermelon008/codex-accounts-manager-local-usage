# Local extension customizations

This fork is pinned to upstream `v0.1.16` / commit `4b1689deafd2d303700c5cc26e6fd285979634e4` and packages as `0.1.16-local.60`.

The root README is the short user guide. The detailed local-integration, seamless-switch, and changelog documents are included in every local VSIX so those links remain available after installation.

## Scope

- Adds an opt-in local Feishu text-import inbox. It is disabled by default, so an unchanged deployment does not create directories, poll files, import credentials, or add network activity. When explicitly enabled on a target host, the extension consumes only a private local queue, writes credentials through VS Code SecretStorage, first quarantines a new or replaced record outside the seamless pool, then refreshes quota through the existing Manager path, and enables the pool only for fresh eligible accounts. The command bot remains limited to Feishu and local queue writes; the inbox never binds behavior to a host address or endpoint.
- Adds Dashboard-local multi-select Free/Plus/Pro plan filters. No selected plan means no plan restriction; one or more selected plans are intersected with the existing visible `A/B/C` groups and hidden-account view. The filter is intentionally not persisted and never changes pool membership, seamless scheduling, or timed quota refresh; visible-page actions and batch selection follow the displayed intersection.
- Adds a per-account manual quota-countdown starter beside the normal quota refresh action. It is offered only while every present primary quota window still reads 100% and its reset time has not advanced beyond its service-reported duration minus five minutes (for example, `4h55m` / `6d23h55m` / `29d23h55m`). Older payloads without a duration retain five-hour/seven-day defaults. The action force-refreshes credentials and quota, sends the fixed text `Hi` through the selected account with no tools, low reasoning, `store:false`, and the SSE streaming mode required by the ChatGPT Codex backend, then force-refreshes quota again. An account-level in-flight guard and ten-minute host-memory suppression prevent duplicate requests while the new countdown is still inside the five-minute display margin; no user prompt or model output is persisted by Manager.
- Exposes a vendor-neutral Gateway integration API in the Manager. The optional Sub2API Gateway VSIX owns its configuration, SecretStorage, inventory observer, downstream key, and the saved-account card actions; it registers only a `Sub2API Gateway` manual-only virtual account containing the downstream route descriptor. Its tracker usage and model-based estimated price are rendered inside that card, and its card-visibility switch is registered dynamically only while the VSIX is installed. The switch only filters the Dashboard card; route selection remains a manual account action. Without that VSIX, the Manager neither reads provider configuration nor starts a Gateway. See [the standalone integration guide](integrations/sub2api-gateway.md).
- Gateway fallback force-refreshes and re-ranks its leading ChatGPT Auth candidate immediately before handoff; a candidate with a failed refresh, no longer valid quota, or missing credentials is excluded only for that fallback transaction. Deferred or failed fallback attempts use a bounded `5 → 10 → 20 → 40 → 60` second retry and surface the next retry in the Gateway card. It reads the ordinary seamless scheduler's unified safety floor without changing that configuration; the Gateway remains outside ordinary ChatGPT source-account scheduling.
- Adds a read-only local Codex token summary below Saved Accounts. The Dashboard and Settings window offer six selectable categories: `24h` (eight 3-hour buckets), `3d` (six half-day buckets merged from four 3-hour buckets), `7d` (seven daily buckets), `14d` (seven two-day buckets), `7w` (seven weekly buckets), and `7m` (seven calendar-month buckets). If no category is selected, the setting normalizes to `24h`.
- Aggregates model, daily, input, output, cached-input, and total-token metadata from the session directory resolved by `$CODEX_HOME` on the target host.
- Does not read or send session text, account identities, auth data, or raw paths to the Dashboard Webview.
- Persists only sanitized aggregates in VS Code global storage. The Dashboard reads the cached result without starting a session scan during activation or cache expiry; the title-row **Refresh Usage** action explicitly starts one fresh scan and can bypass the freshness window, while still using the shared lease to avoid concurrent hosts duplicating work. The freshness deadline remains capped at the next local midnight so a cached previous-day view is marked stale. Before streaming files, the scanner excludes session files whose mtime is safely outside the retained window; while streaming, it parses only `session_meta`, `turn_context`, `token_count`, and inter-agent turn-boundary metadata instead of allocating object graphs for conversation and tool-output records. Token events advance a per-rollout cumulative high-water mark, so repeated/stale reports are ignored. Spawned subagent rollouts use the copied parent history only as their initial baseline and begin contributing after their own trigger-turn boundary. Each host adopts a strictly newer shared result by `calculatedAt`, and an expiring scan lease deduplicates work across extension hosts.
- The scanner retains four local days of 3-hour aggregates for `24h`/`3d` and up to 370 local days of sanitized daily aggregates for longer ranges. The first explicit **Refresh Usage** after enabling `7w` or `7m` backfills only the missing daily coverage; later refreshes scan the short window and merge it into the retained daily cache. All six categories are projected from these cached buckets, so switching tabs does not rescan files and enabling/disabling a category does not by itself start a scan.
- Shows an optional estimated standard OpenAI API price in USD between total and input tokens, and alongside each usage bar as `Token (US$price)`. Unknown models stay in range totals but are omitted from the model-distribution list. It is an informational estimate only, not a Codex subscription bill.
- The fail-closed usage compatibility check accepts the current aggregate `local-enhancements` manifest and the legacy `local-usage-dashboard` manifest; a reviewed aggregate build must not hide the usage block solely because the manifest scope expanded.

The displayed values are local session observations, not ChatGPT account quota or billing data.

## Experimental account hot switch

- Adds a bundled local CLI shim that proxies the official Codex app-server over stdio; it is not a resident HTTP service.
- Forces Responses HTTP streaming inside the installed runtime because Codex `0.144.2` caches an authenticated WebSocket per loaded thread. This ensures the next turn on the same thread resolves the newly selected account instead of continuing to bill the old WebSocket identity.
- Merges the official current-provider `thread/list` view across provider IDs without rewriting local history, so sessions created before and after the HTTP provider was introduced remain visible together while the runtime is installed.
- Adds an explicit multi-account seamless-switch pool with selectable 20%, 25%, 33%, or 50% bands and one low-quota / exhaustion setting: After exhaustion, 1%, 3%, or 5% (default 3%). Fresh quota payloads, not Free/Plus plan labels, classify ordinary scheduling as `windowed` (usable five-hour and long-term windows), `reserve` (explicitly no five-hour window and a usable long-term window), or `unknown` (missing, stale, or erroneous data). Ordinary band scheduling rotates non-Free windowed accounts first. A nonzero threshold starts an immediate transaction at the matching usable five-hour/long-term floor or a structured usage-limit signal; targets must remain strictly above it. Low-quota/exhaustion selection chooses a windowed target with the highest five-hour then weekly headroom, or, only when none is eligible, the reserve target with the highest weekly headroom. Equal quota uses plan preference Free/K12 → Plus → Pro, then existing stable tie-breaks. Free/K12 targets use a two-minute freshness bound even when they are valid reserve accounts; no forced refresh is performed. After exhaustion retains band scheduling but requires every conversation in the observed active batch to terminate for quota exhaustion before an in-band switch, with a six-hour maximum observation window. Hidden accounts are removed from this pool immediately, excluded from every automatic/manual switching target, and automatically return to the pool when unhidden. Accounts can additionally be assigned to `A/B/C` groups: the Dashboard group filters persist independently from pool membership, limit only seamless candidates and the one-click Dashboard quota refresh, and leave ungrouped non-hidden accounts always visible and eligible. Saved-account cards are paged at 50; the Dashboard refresh button uses the current page, while timed quota refresh uses only the first non-hidden page of enabled groups. This configuration, scheduler state, and fail-closed execution are independent of upstream Auto Switch.
- A successful bulk hide clears only the corresponding card selections. The Dashboard also exposes a one-click `weekly <3%` hide action scoped to the current visible account list; it excludes hidden accounts and accounts without a recognized weekly window.
- A one-click `weekly >90%` recovery action scans all hidden accounts, including accounts in currently disabled groups. It atomically unhides each eligible account, restores its seamless-pool membership, and clears its `A/B/C` group; regular bulk unhide continues to preserve the group.
- The unified nonzero threshold replaces the separate 1% exhaustion-protection toggle. It bypasses the normal baseline and quota-band grace period for usable five-hour or long-term quota, and for structured `usageLimitExceeded`; the configured ordinary-turn policy remains common to every switch type. A verified Free/K12 source does not exclude valid Free/K12 reserve targets: they are eligible when their explicit long-term quota is above the selected threshold and their quota was refreshed within two minutes. The selector still prefers higher real quota windows before plan tier, and never forces a refresh merely to make a candidate eligible. Terminal `error` notifications and structured `turn/start` RPC rejections carrying `usageLimitExceeded`, plus compatible failed-turn payloads, enter a six-hour recovery journal so already-stopped ordinary threads can receive one continuation; persistent Goals are paused/resumed and `usageLimited` Goals are explicitly reactivated after the switch. A separate runtime-local model-capacity queue handles `Selected model is at capacity. Please try a different model.` / `server_overloaded` independently per thread, waits one minute, and retries `Continue.`; an OAuth seamless switch claims waiting entries before its timer, while a Gateway route switch does not. In After exhaustion mode, the separate batch decision is canceled by newer work, a normal peer completion, interruption, or a non-quota failure, without clearing that recovery journal. The extension-host monitor performs a two-second bounded-scalar poll for every threshold; nonzero values act on fresh failure counts, while After exhaustion acts only on a ready batch. It serializes requests, retries a deferred selection after ten seconds, and backs off an unavailable status RPC for thirty seconds. Non-sensitive runtime counters expose observed failures, batch readiness, capacity recovery counts, and successful ordinary/Goal recoveries for live diagnostics.
- Gives quota-band/manual switches a configurable 60-second grace period, queues new turn starts, and never changes authentication while an old turn remains active. Low-quota and After exhaustion switches start at the common policy boundary without this initial grace period.
- Pauses active persisted Goals, interrupts an over-grace Goal turn, and restores the Goal after success, rollback, cancellation, or manager disconnect without changing thread-sticky workspace and permission settings.
- Offers opt-in ordinary-turn interruption and one-shot same-thread continuation; the default safely defers the switch and retries on a later quota refresh.
- Leaves multi-agent subagent recovery to its parent agent. Before a one-shot continuation, the shim reads only thread metadata; a thread with a parent or subagent source is not given a direct `turn/start`, because current app-server rejects direct input to those threads.
- Keeps a bounded terminal-turn ledger so late `turn/start` responses cannot resurrect completed turns. If app-server reports that a tracked turn ID has been replaced by a newer active turn in the same thread, the shim resynchronizes that exact ID and retries the interrupt once; explicit already-inactive results are also reconciled. It only auto-continues after the replacement turn confirms `interrupted`, and retries deferred cross-window convergence after the safe boundary.
- Adds a user-facing Seamless Switching master toggle. Turning it off restores the original persisted-account/reload workflow without uninstalling the runtime; the quota-band scheduler, ordinary-turn policy, and Goal recovery remain child settings of this mode.
- Adds a per-account pool switch at the lower-left of every saved-account card plus explicit Set Pool and Remove from Pool batch actions; a pool with fewer than two members is valid and simply leaves band scheduling inactive.
- On Remote-SSH, WSL, and Dev Container hosts, avoids `chatgpt.cliExecutable` entirely. The install command refuses to proceed while that application-scoped setting remains, then saves the remote bundled CLI as a same-directory backup and replaces its path with a reversible link to the manager launcher. This keeps one client machine's local path from overriding Codex on another client connected to the same host.
- Treats either a successful `initialize` response or the client's `initialized` notification as a usable app-server handshake. If hot switching is enabled but the runtime bridge is not ready, switching fails closed and does not fall back to rewriting persisted auth.
- Keeps the existing reload behavior only when the experimental feature is disabled. A failed or deferred in-flight transaction leaves the persisted account unchanged instead of writing new auth while a turn is active.
- Supports a safe first seamless switch after every managed account has been deleted. Runtime protocol v11 captures the currently valid `auth.json` only as an in-memory rollback snapshot, confirms its identity against the live app-server, and restores it if the target switch fails; the old identity is not silently imported into the account list. A socket timeout retains that snapshot only while a bounded `operationId` reconciliation is pending, then clears it on a confirmed result or rollback. The same rollback material protects an installed optional Gateway-to-ChatGPT fallback transaction.
- Adds a compact, prospective account-window token counter below each eligible account card. The shim batches only an opaque local account ID, thread ID, and timestamp at managed-turn boundaries; the existing 15-minute metadata scan attributes already-present `token_count` deltas to the matching current five-hour or long-term quota reset window. Account aggregation retains up to 31 days of managed metadata independently of the 14-day local dashboard, and coalesces `reset_at` observations within one minute into the current reset boundary so a small reporting drift cannot split one quota cycle. A changed reset boundary still immediately displays zero until new attributed metadata arrives. A single runtime `primary` window is classified by its actual duration, so a Plus-style long window is not mistaken for a five-hour quota. It does not send a per-token IPC request, perform a second session-body scan, or make network requests. History before the first managed turn is not backfilled.
- Never writes credentials into the shim configuration or logs. Runtime IPC is scoped to the current extension-host PID and local user.
- Separates the stable account-record email from the access-token runtime email reported by Codex. A runtime alias is accepted only after the access token's user ID matches the managed account, so legitimate alias drift does not trigger rollback without weakening fail-closed identity checks.
- Adds a credential-free `verify:seamless-auth` check that starts a selected real Codex binary with synthetic accounts and proves an A-to-B auth change on the same thread. This must be rerun after a Codex protocol/runtime upgrade.

See [HOT_SWITCH.md](HOT_SWITCH.md) for setup, exact scheduling rules, concurrency semantics, compatibility limits, and rollback.

## Cross-host coordination

- Account index, token mirror, and quota-mirror writes use unique temporary files, atomic replacement, expiring shared leases, and three-way account merges. Concurrent Mac, Windows, and remote extension hosts cannot overwrite a newly imported/deleted account merely by flushing an older in-memory snapshot.
- File watching is backed by a two-second stat/revision poll so Remote-SSH and network-filesystem hosts still observe changes when an event is delayed or dropped.
- Background token refresh, quota scanning, and seamless scheduling use separate expiring leases. The Dashboard's local usage scan is manual-only in this build. Another host can reap a lease after its owner exits, while an explicit manual refresh remains available.
- Every physical app-server identity or provider-route handoff—automatic seamless scheduling, manual selection, external-auth convergence, virtual Gateway selection, and Gateway fallback—passes through one renewable cross-host runtime lease. A short control-socket failure keeps that lease while the manager queries the shim's bounded operation status; a restarted shim yields an explicit reload-required failure instead of a competing switch. Route changes wait for the same turn/Goal barrier; an active stream is never migrated in place.
- Each app-server keeps its own turn barrier and converges to the shared active account at a safe boundary. This is deliberate eventual convergence, not a cross-process atomic switch; an already-running turn can finish with its original account.
- The original shared local-usage cache contains aggregate statistics and timing metadata only. The separate account-window cache stores only opaque local record IDs, reset boundaries, and token totals with `0600` permissions; neither cache contains conversation text, email, remote account IDs, credentials, thread IDs, or full session paths.

## Equivalent API price

The default bundled rate table uses the standard API input / cached-input / output USD prices documented for [GPT-5.6 Terra](https://developers.openai.com/api/docs/models/gpt-5.6-terra), [GPT-5.6 Luna](https://developers.openai.com/api/docs/models/gpt-5.6-luna), [GPT-5.6 Sol](https://developers.openai.com/api/docs/models/gpt-5.6-sol), and [GPT-5.5](https://developers.openai.com/api/docs/models/gpt-5.5). Cached input is estimated separately; the scanner does not expose enough information to price cache writes. Unknown models are excluded and flagged in the price-card subtitle.

The estimate deliberately excludes tool fees, long-context premiums, cache writes, taxes, exchange rates, and any subscription-specific pricing. Review and update the bundled table whenever API pricing changes.

## Dashboard settings

The existing Dashboard Settings window has a **Local Usage Dashboard** section with a multi-select enabled-range panel and a **Show Estimated API Price** toggle. The corresponding VS Code configuration keys are:

```json
"codexAccounts.localUsageEnabledRanges": ["24h"],
"codexAccounts.localUsageShowEquivalentPrice": true
```

Changing the enabled list changes only the available Dashboard tabs and the next required cache coverage; it never changes saved accounts or quota refreshes. The setting update itself does not scan sessions. The Dashboard's explicit **Refresh Usage** action is the only way to start a new local session scan; when a newly enabled long category is missing coverage, that scan performs the one-time daily backfill described above. The legacy `localUsageDefaultRange` and numeric `localUsageDefaultRangeDays` settings remain read-only migration sources.

Seamless scheduling exposes an independent `codexAccounts.seamlessSwitchLowQuotaEnabled` toggle and `codexAccounts.seamlessSwitchThreshold` with allowed values `0` (After exhaustion), `1`, `3`, and `5` (default `3`). When the new toggle has not yet been saved, it inherits the old quota-band switch state for compatibility; once saved, the two switches are independent. Turning it off prevents low quota, structured `usageLimitExceeded`, and exhaustion batches from starting a new automatic switch, without disabling quota-band switching. It does not alter upstream Auto Switch thresholds. Existing explicit legacy settings are read once for compatibility until the threshold is saved: the former 1% protection maps to `1`; a former `2%` reserve floor maps to `3`.

## Update safety

Never edit a Marketplace extension's source or bundle in place. Install the generated VSIX and disable automatic updates for this extension. The remote seamless-runtime command is a deliberately narrow, reversible exception: it renames only the remote bundled Codex executable to a same-directory backup and makes the original executable path a launcher symlink. Removing the runtime restores that backup only if the link still belongs to this manager; it never replaces another tool's link.

## Installation

After `npm run package` produces a VSIX, use **Extensions: Install from VSIX…** in the VS Code window connected to the target Remote-SSH/WSL/Container host. This project is intended for that remote extension host's extension storage.

Set the following in the target user's VS Code settings, or disable Auto Update on this extension from the Extensions view:

```json
"extensions.autoUpdate": false,
"extensions.autoCheckUpdates": false
```

When a Marketplace update is deliberately installed, this local feature is not reattached automatically. The stock extension runs without the local usage block until a newly reviewed VSIX is built and installed.

Before taking a newer upstream version:

1. Fetch the candidate source and ask Codex to review its diff against the pinned baseline.
2. Reapply/review this customization and update `local-customization.json` only after the review.
3. Update the reviewed SHA-256 values, run `npm run verify:customization`, tests, and package a new VSIX.

`npm run package` is intentionally fail-closed. It refuses to package if any changed file falls outside the reviewed list or if any protected file no longer matches its reviewed SHA-256 value.

The development toolchain keeps ESLint 8 for the repository's `.eslintrc.json` configuration and pins VSCE 2.32 with a compatible Cheerio release so the documented package command also runs in the current Node 18 release shell. These are development-only dependencies; the generated extension runtime does not ship them.

The build pins `@vscode/vsce` to `2.32.0` and Cheerio to `1.0.0`, so packaging remains reproducible on the repository host's Node `18.19+` runtime. Re-evaluate these pins together when the build environment moves to Node 20 or newer.

When a reviewed customization intentionally removes an upstream file, record it in `removedFiles` in `local-customization.json`. The baseline check then requires that file to remain absent; it does not silently accept an unreviewed deletion.
